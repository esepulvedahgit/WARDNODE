{# ── 1. Visión general ───────────────────────────────────────── #}

1 · Visión general

El stack OBS tiene una arquitectura de dos capas independientes:

CapaServiciosCuándo arranca
Colección Alloy, Loki, Prometheus, nginx-exporter Siempre — con docker compose up base. No requiere módulo OBS activo.
Visualización Grafana Solo con --profile obs o al activar el módulo OBS desde la consola.

Esta separación garantiza que los logs y métricas se capturan desde el primer contenedor levantado, minimizando el riesgo de perder datos de observabilidad antes de que el módulo esté activo.

{# ── 2. Capa de colección ────────────────────────────────────── #}

2 · Capa de colección (siempre activa)

Los cuatro servicios de colección arrancan con el stack base y no requieren intervención manual:

ServicioFunciónLímite de memoria
Alloy (Grafana Alloy) Agente colector. Hace stream de logs del contenedor proxy vía Docker y scrape de métricas Prometheus. También provee métricas de sistema mediante prometheus.exporter.unix. 256 MB
Loki Almacén de logs. Retención por defecto de 30 días. Fuente autoritativa para logs HTTP raw (acceso, errores, URIs, códigos de respuesta). 256 MB
Prometheus Almacén de métricas de series temporales. Recibe scrapes de Alloy y nginx-exporter. 256 MB
nginx-exporter Expone métricas del módulo ngx_http_stub_status de Nginx vía HTTP para que Prometheus las scrape. 32 MB

La capa de colección no requiere módulo OBS activo — siempre recoge datos. Fluent Bit ha sido eliminado del stack; Alloy cubre toda la colección.

{# ── 3. Capa de visualización ────────────────────────────────── #}

3 · Capa de visualización (Grafana)

Grafana es la única pieza de visualización y se gestiona de forma independiente de la colección:

  • Activar desde la consola: panel OBS → botón "Activar módulo OBS". Esto levanta únicamente el contenedor wardnode-grafana.
  • En producción: docker-compose.vps.yml incluye el profile obs preconfigurado. Las configuraciones de OBS se copian desde la imagen de la consola a volúmenes nombrados antes de que los contenedores OBS arranquen.
  • Acceso: Grafana se sirve en /obs/ vía un bloque nginx (obs.conf) inyectado dinámicamente en el contenedor proxy al activar el módulo.

{# ── 5. Invariante importante ────────────────────────────────── #}

5 · Invariante importante

Los conteos de eventos WAF deben leerse siempre desde PostgreSQL, ya sea desde el dashboard WAF Analytics (03) o desde la página /proxy/ de la consola.

Loki almacena líneas de log crudas con retención de 30 días. Los números de Loki y PostgreSQL no coincidirán — y eso es completamente esperado. PostgreSQL deduplica transacciones ModSecurity por transaction_id, mientras que Loki almacena cada línea de log individualmente.

Nunca uses los conteos de Loki para reportar incidentes WAF. Usa siempre PostgreSQL como fuente autoritativa.
{# ── 6. Acceso y pantalla completa ───────────────────────────── #}

6 · Acceso y pantalla completa

Una vez el módulo OBS está activo:

OpciónURLDescripción
Grafana embebido /obs/ Grafana sirviéndose a través del proxy WAF. El acceso requiere módulo OBS activo.
Pantalla completa /modules/obs/fullscreen Vista embebida de Grafana en la consola WardNode a pantalla completa. Accesible desde el panel OBS con el botón "Pantalla completa".

Si el módulo no está activo, el acceso a /obs/ devuelve un error 502 (el proxy no tiene configurado ese bloque de ubicación).
