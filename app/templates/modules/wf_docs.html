1 · Visión general

WardNode WF gestiona el firewall UFW del servidor host desde la consola web, sin necesidad de SSH directo. El módulo permite crear, eliminar y listar reglas de firewall, proteger puertos expuestos por Docker y aplicar rate-limiting SSH, todo desde el navegador.

La comunicación sigue el siguiente flujo:

Consola Flask (contenedor)
      │  socket Unix
      ▼
/app/sockets/wardnode-wf.sock
      │
      ▼
Agente host Python (wardnode-wf-agent.py)
      │  subprocess.run (nunca shell=True)
      ▼
UFW / iptables (host)

El agente corre en el host como root:wardnode bajo systemd, lo que garantiza que solo el proceso autorizado puede escribir en el socket y ejecutar comandos con privilegios.

{# ── 2. Arquitectura del agente ──────────────────────────────── #}

2 · Arquitectura del agente

El sistema usa un protocolo de mensajes JSON sobre un socket Unix con prefijo de longitud (4 bytes big-endian):

CapaComponenteResponsabilidad
Contenedor Flask modules/socket_client.py Serializa comandos JSON, envía con prefijo de longitud, recibe respuesta.
Socket Unix /app/sockets/wardnode-wf.sock Canal de comunicación bind-montado desde el host al contenedor.
Agente host wardnode-wf-agent.py Re-valida todos los argumentos con regex antes de llamar a subprocess.run (nunca shell=True). Los comandos están en una lista blanca (ACTIONS).

La variable de entorno WF_SOCKET_PATH controla la ruta del socket en el contenedor (default: /app/sockets/wardnode-wf.sock). La validación de entrada es dual-layer: Flask valida en socket_client.py antes de enviar; el agente re-valida de forma independiente — nunca confía en el llamador.

{# ── 3. Instalación del agente ───────────────────────────────── #}

3 · Instalación del agente

El agente host se instala desde el panel WF de la consola. El proceso es el siguiente:

  1. Desde el panel WF, hacer clic en "Generar clave" para crear el par de claves SSH que usará WardNode para conectarse al host.
  2. Añadir la clave pública generada al archivo ~/.ssh/authorized_keys del servidor host.
  3. Hacer clic en "Instalar agente". WardNode se conectará por SSH a host.docker.internal usando la clave privada del admin.
  4. El script host-agent/install.sh (ejecutado como root) instala: grupo wardnode, el agente wardnode-wf-agent.py, el servicio systemd, habilita UFW e instala CrowdSec (desactivado hasta que se active el módulo DDoS).
RequisitoDescripción
SSH accesible en host.docker.internal:22El servidor debe aceptar conexiones SSH desde el contenedor. Requiere extra_hosts: host-gateway en docker-compose.vps.yml.
Python 3 disponible en el hostEl agente es un script Python. Python 3.8+ recomendado.
UFW disponibleufw debe estar instalado en el sistema (apt install ufw).
Privilegios rootEl script de instalación debe ejecutarse como root para crear el servicio systemd.
{# ── 4. Inicialización obligatoria ───────────────────────────── #}

4 · Inicialización obligatoria (primera vez)

Antes de poder crear reglas, se debe ejecutar el paso "Inicializar firewall" (botón en el panel WF). Esta acción aplica la política por defecto de UFW:

  • ufw default deny incoming — bloquea todo el tráfico entrante no explícitamente permitido.
  • ufw default allow outgoing — permite todo el tráfico saliente.
Importante: puerto SSH. Durante el init se solicita el puerto SSH actual del servidor. Introducirlo incorrectamente bloqueará el acceso SSH al servidor. WardNode añade automáticamente una regla allow para el puerto indicado antes de activar UFW.

Hasta completar este paso, los paneles "Permitir" y "Bloquear" están deshabilitados en la UI.

{# ── 5. Gestionar reglas ─────────────────────────────────────── #}

5 · Gestionar reglas (allow / deny / delete)

Una vez inicializado el firewall, el panel WF permite gestionar reglas UFW de forma visual:

AcciónCómoNotas
Añadir regla allow Formulario "Permitir": especificar puerto (número o rango 8080:8090) y protocolo (tcp / udp / any). Opcionalmente restringir a una IP origen. Ejemplo: puerto=8080, proto=tcp, from=192.168.1.0/24
Añadir regla deny Formulario "Bloquear": mismos campos que allow. Bloquea el acceso al puerto indicado.
Eliminar regla Desde la lista de reglas activas, icono de papelera. La eliminación es inmediata en UFW.

Las reglas se aplican inmediatamente en UFW — no requieren recarga manual ni reinicio del agente.

{# ── 6. Puertos publicados por Docker ────────────────────────── #}

6 · Puertos publicados por Docker

Docker expone puertos directamente en el host usando la chain DOCKER de iptables, que tiene precedencia sobre UFW. Esto significa que un puerto expuesto por Docker puede ser accesible desde el exterior aunque UFW no tenga una regla allow explícita.

El panel "Puertos Docker" lista los puertos expuestos por los contenedores del stack WardNode. Para cada puerto se puede aplicar "Proteger puerto", que añade una regla iptables explícita en raw/PREROUTING para que UFW controle el acceso antes de que la chain DOCKER lo intercepte.

Recomendación: proteger el puerto del proxy (80/443) antes de configurar el WAF en producción. Sin esta protección, el tráfico puede llegar al proxy saltándose las reglas UFW.
{# ── 7. SSH rate-limit ───────────────────────────────────────── #}

7 · SSH rate-limit

El botón "Limitar SSH" activa ufw limit ssh, que bloquea automáticamente las IPs que intentan más de 6 conexiones SSH en 30 segundos. Es una protección básica contra ataques de fuerza bruta por SSH.

Conflicto con CrowdSec: no activar este límite si ya tienes el módulo CrowdSec (DDoS) activo con protección SSH. Ambos mecanismos pueden interferir, generando bloqueos inesperados o reglas duplicadas.

El botón "Quitar límite" revierte la regla a un allow ssh simple, eliminando el rate-limiting.

{# ── 8. IPv6 ─────────────────────────────────────────────────── #}

8 · IPv6

El toggle IPv6 controla si UFW aplica reglas sobre tráfico IPv6, modificando la variable IPV6=yes/no en /etc/default/ufw.

EstadoEfecto
Activado (yes)Las reglas UFW aplican tanto a IPv4 como a IPv6. Las conexiones entrantes IPv6 quedan sujetas a las mismas reglas.
Desactivado (no)Las reglas solo aplican a IPv4. El tráfico IPv6 no está controlado por UFW.

Cambiar este toggle requiere que UFW se reinicie para aplicar el cambio en /etc/default/ufw. El agente gestiona esto automáticamente.

{# ── 9. Advertencias críticas ────────────────────────────────── #}

9 · Advertencias críticas

Puerto 5000 (consola WardNode). Al activar el módulo WF con UFW default deny incoming, el puerto 5000 de la consola queda bloqueado. Antes de inicializar, configurar el acceso al panel en Ajustes → Acceso al panel con tu dominio y asegurarse de que el proxy redirige correctamente. Acceder siempre por el dominio, nunca por IP:5000.
Puerto SSH incorrecto durante el init. El puerto SSH se solicita durante la inicialización y se añade automáticamente como regla allow. Si se introduce un puerto incorrecto, UFW bloqueará el acceso SSH real y el servidor quedará inaccesible por SSH. Verificar el puerto SSH antes del init con ss -tlnp | grep sshd.
Docker y UFW. Los puertos publicados por Docker pueden bypassear UFW. Usar el panel "Puertos Docker" para proteger los puertos críticos del stack.
