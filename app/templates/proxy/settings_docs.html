1 · Visión general

La pantalla de Ajustes concentra la configuración global de la consola: comunicaciones salientes (SMTP, syslog), datos de geolocalización, dominio de acceso y seguridad de secretos.

Solo accesible para administradores. Los cambios aquí afectan a toda la instancia de WardNode, no a un sitio concreto.

{# ── 2. SMTP ─────────────────────────────────────────────────── #}

2 · SMTP — correo saliente

WardNode usa un servidor SMTP para enviar: alertas SOC, notificaciones de backup y resets de contraseña.

Campos de configuración

CampoDescripción
Servidor SMTPHostname o IP del servidor de correo saliente.
PuertoPuerto del servidor (25, 465, 587, etc.).
UsuarioCuenta de autenticación SMTP.
ContraseñaCifrada en reposo con WARDNODE_SECRET_KEY.
Dirección remitenteDirección From: que aparece en los correos enviados.
TLSActivar si el servidor requiere STARTTLS o SSL/TLS.

El botón "Enviar correo de prueba" verifica la configuración enviando un mensaje al email del administrador.

Sin SMTP configurado, los resets de contraseña por email y las notificaciones de backup no funcionarán. Los alertas SOC por correo tampoco estarán disponibles.
{# ── 3. Syslog ───────────────────────────────────────────────── #}

3 · Syslog RFC5424 — reenvío a SIEM

WardNode puede reenviar eventos WAF y entradas del audit log a un servidor syslog externo (SIEM, Splunk, ELK, etc.).

Protocolo de transporte

Soporta UDP y TCP. TCP soporta RFC6587 octet-counting, que permite mensajes de cualquier longitud sin ambigüedad de delimitación.

Campos de configuración

CampoDescripción
ServidorHostname o IP del servidor syslog destino.
PuertoPuerto UDP/TCP del servidor (por defecto 514).
ProtocoloUDP o TCP.
Facilidad syslogFacility RFC5424 (local0–local7, etc.).

El botón "Probar syslog" envía un mensaje de prueba al servidor configurado para verificar la conectividad.

Cómo funciona internamente

Un thread daemon (syslog-forwarder) revisa cada 10 segundos las nuevas entradas en modsec_raw_log y audit_log, las serializa como mensajes RFC5424 con cuerpo JSON y las envía al servidor configurado.

Semántica at-least-once: si el servidor no está disponible, los cursores no avanzan y los eventos se reenvían al recuperarse. No hay pérdida de datos por indisponibilidad temporal.

El reenvío syslog no incluye logs de acceso HTTP de Nginx — esos van a Loki vía Alloy (módulo OBS). Solo se reenvían eventos WAF (modsec_raw_log) y acciones de auditoría (audit_log).
{# ── 4. GeoIP ────────────────────────────────────────────────── #}

4 · GeoIP — base de datos de geolocalización

WardNode usa la base de datos GeoLite2-Country de MaxMind para el bloqueo por país (GeoIP) en el WAF.

Requisitos

  • Cuenta gratuita en MaxMind.
  • Credenciales MAXMIND_ACCOUNT_ID y MAXMIND_LICENSE_KEY configuradas en Ajustes.

El botón "Descargar base GeoIP" descarga o actualiza el archivo GeoLite2-Country.mmdb dentro del contenedor de la consola.

Sin la base descargada, el bloqueo por país no funciona aunque haya países en la blocklist de un sitio. La variable $geo_blocked en Nginx valdrá siempre 0.

Actualización periódica

MaxMind actualiza GeoLite2-Country semanalmente. Se recomienda volver a descargar la base periódicamente para mantener la precisión geográfica actualizada.

{# ── 5. Console-site ─────────────────────────────────────────── #}

5 · ⚠️ Acceso al panel (console-site)

⚠️ Configura esto ANTES de activar el módulo WF. Al activar WF con ufw default deny incoming, el puerto 5000 queda bloqueado. Si no hay console-site configurado, la consola quedará inaccesible desde el exterior.

Define el dominio (y opcionalmente el puerto) desde el que los administradores acceden a la consola WardNode.

Formato

Solo el dominio, sin protocolo ni barra final:

CorrectoIncorrecto
mi-consola.ejemplo.comhttps://mi-consola.ejemplo.com/
mi-consola.ejemplo.com:8080http://mi-consola.ejemplo.com

Qué hace al configurarlo

WardNode genera un server block Nginx para el dominio de la consola y abre el puerto correspondiente en UFW, de modo que el acceso de administración quede permitido incluso tras activar el modo restrictivo del firewall.

{# ── 6. Reset secretos ───────────────────────────────────────── #}

6 · ⚠️ Reset de secretos cifrados

⚠️ Usar solo en emergencia. Esta acción elimina TODOS los secretos almacenados de forma irreversible. Solo úsala si has perdido WARDNODE_SECRET_KEY y necesitas empezar de cero.

WardNode cifra secretos sensibles (API keys SOC, credenciales SMTP, configuración syslog, clave MaxMind) con WARDNODE_SECRET_KEY usando cifrado Fernet simétrico.

El botón "Resetear secretos cifrados" elimina de la base de datos todos los secretos almacenados:

  • Contraseña SMTP
  • Credenciales MaxMind GeoIP
  • API keys de proveedores LLM (SOC)
  • Token de Telegram (SOC alertas)
  • Configuración syslog cifrada

Tras el reset, deberás volver a introducir todas las credenciales. Las otras configuraciones (sitios, reglas WAF, eventos) no se ven afectadas.

{# ── 7. Limpiar eventos WAF ──────────────────────────────────── #}

7 · Limpiar eventos WAF

Elimina todos los registros de la tabla attack_event (historial de eventos WAF detectados o bloqueados por ModSecurity).

Útil en estos escenarios:

  • Durante pruebas o puesta en marcha, para reiniciar el historial sin datos de test.
  • Tras una migración, para resetear el dashboard con datos limpios del nuevo entorno.
  • Para cumplimiento normativo que requiera borrado de datos históricos.
⚠️ Acción irreversible. El historial WAF no se puede recuperar después del borrado. Los incidentes SOC relacionados con esos eventos también perderán su contexto de AttackEvents.
