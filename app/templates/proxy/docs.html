1 · Visión general del plano de proxy

WardNode separa completamente el plano de gestión del plano de tráfico. La consola Flask (puerto 5000) nunca maneja tráfico de usuarios finales: solo genera archivos de configuración Nginx que el contenedor proxy lee y aplica.

Tráfico externo (internet)
      │  80 / 443
      ▼
┌──────────────────────────────────────────┐
│  Contenedor proxy                        │
│  Nginx + ModSecurity (OWASP CRS)         │
│                                          │
│  Lee: /etc/nginx/generated/*.conf        │  ◄── generados por la consola
│  Aplica: WAF, TLS, rate limit, headers   │
└──────────────────────┬───────────────────┘
                       │  proxy_pass http://upstream:puerto
                       ▼
              Aplicación protegida
       (contenedor, proceso en host, VM, LAN…)

┌──────────────────────────────────────────┐
│  Consola Flask  (puerto 5000)            │
│  Solo plano de gestión                   │
│  Escribe  →  generated/nginx/*.conf      │
│  Recarga  →  docker exec nginx -s reload │
└──────────────────────────────────────────┘

Cómo se define el destino de cada sitio

Cada sitio tiene un campo upstream_url. La consola lo parsea y genera directamente:

proxy_pass http://<host>:<puerto>;
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

El valor se inyecta tal cual — no hay bloque upstream {} nombrado. El proxy intentará alcanzar ese host por la red que tenga disponible.

Tres alcances de upstream

AlcanceEjemploRequisito
A · Red interna Docker http://mi-app:8080 La app debe estar en la misma red bridge que el proxy (solo funciona en DEV)
B · Red del host http://127.0.0.1:3000 Módulo WF activo + puerto no reservado
C · Red externa / LAN http://192.168.1.10:8088 Conectividad de red entre el servidor y la LAN (túnel en VPS)
DEV vs PROD: el modo de red del proxy cambia entre entornos y afecta qué alcances son posibles. En desarrollo el proxy está en la red bridge wardnode_internal (resuelve nombres de servicio Docker). En producción usa network_mode: host (comparte la red del servidor, no resuelve nombres del bridge). Esto se explica en detalle en cada sección.
{# ── 2. Alcance A — Red interna Docker ──────────────────────── #}

2 · Alcance A — Red interna de WardNode (Docker)

La aplicación corre como contenedor Docker en la misma red bridge que WardNode. El upstream se registra por nombre de servicio (ej. http://mi-app:8080) en lugar de por IP.

En desarrollo (docker-compose.yml)

El proxy tiene IP fija 172.30.0.10 en la red wardnode_internal (172.30.0.0/24). Al estar todos los servicios en el mismo bridge, Docker provee DNS interno: el proxy resuelve mi-app → IP del contenedor de la app. El alcance A funciona completamente en desarrollo.

Para unir tu contenedor de aplicación a la red de WardNode, declara en tu docker-compose.yml:

# docker-compose.yml de tu aplicación
services:
  mi-app:
    image: mi-imagen:latest
    networks:
      - wardnode_internal   # misma red que el proxy

networks:
  wardnode_internal:
    external: true          # red ya creada por WardNode

Luego registra el sitio en WardNode con upstream_url = http://mi-app:8080.

En producción (docker-compose.vps.yml) — matiz crítico

⚠️ El alcance A no funciona en producción.
En producción el proxy usa network_mode: host: comparte la pila de red del servidor directamente y no está conectado a la red bridge wardnode_internal. Por eso no tiene acceso al resolver DNS de Docker y no puede resolver nombres de servicio como mi-app, loki o db.

Si tu aplicación corre en un contenedor en producción, las alternativas son:

AlternativaCómoRecomendación
Publicar puerto al host y usar loopback Añadir ports: ["127.0.0.1:8080:8080"] en el contenedor de tu app. Registrar el upstream como http://127.0.0.1:8080 (Alcance B). ✅ Recomendada — el módulo WF protege el puerto
IP del contenedor en el bridge Obtener la IP con docker inspect mi-app y usar http://172.30.0.x:8080. ⚠️ Frágil — la IP cambia al recrear el contenedor

La opción recomendada es publicar el puerto al host y registrarlo como upstream de loopback. Ver Alcance B para los requisitos.

Tabla DEV vs PROD

DesarrolloProducción

¿Resuelve http://mi-app:8080?✅ Sí — mismo bridge❌ No — no está en el bridge

{# ── 3. Alcance B — Red del host ─────────────────────────────── #}

3 · Alcance B — Red del host (127.0.0.1)

La aplicación escucha en el loopback del propio servidor donde corre WardNode. Cubre dos casos:

  • Procesos nativos (Node.js, Python, Java, etc.) ejecutados directamente en el host.
  • Contenedores Docker que publican su puerto al loopback del host con ports: ["127.0.0.1:8080:8080"].

En producción (network_mode: host), los tres hosts siguientes son equivalentes y apuntan al mismo lugar — el propio servidor:

UpstreamEquivale a
http://127.0.0.1:3000El loopback del servidor donde corre WardNode
http://localhost:3000
http://host.docker.internal:3000

Requisito: módulo WardNode WF

WardNode exige que el módulo WF (WardNode Firewall) esté activo antes de permitir un upstream de loopback. Si WF no está activo, la consola rechaza el upstream con un error al crear o editar el sitio. Actívalo en Módulos.

Puertos reservados (bloqueados)

Los siguientes puertos están reservados y no pueden usarse como upstream de loopback:

PuertoMotivo
22SSH del servidor
80Nginx (el propio proxy WAF)
443Nginx TLS (el propio proxy WAF)
5000Consola de gestión WardNode

Cualquier otro puerto disponible es válido. El formulario de sitio usa http://127.0.0.1:3000 como ejemplo.

Qué hace el módulo WF con el puerto

Protección automática vía iptables: al registrar un upstream de loopback, el módulo WF añade una regla en iptables raw/PREROUTING que bloquea el acceso directo a ese puerto desde cualquier origen excepto el proxy WAF. Esto evita que el servicio quede accesible sin pasar por el WAF si alguien conoce el puerto. Al eliminar el sitio, la regla se retira automáticamente.

Ejemplo de registro

# 1. Tu app escucha en el puerto 3000 del servidor
#    (proceso nativo o contenedor con ports: ["127.0.0.1:3000:3000"])

# 2. En WardNode, registra el sitio con:
upstream_url = http://127.0.0.1:3000

# El proxy generará:
proxy_pass http://127.0.0.1:3000;

# WF bloqueará el acceso directo al :3000 desde el exterior.
{# ── 4. Alcance C — Red externa / LAN ────────────────────────── #}

4 · Alcance C — Red externa / LAN (192.168.1.10:8088)

La aplicación corre en otro servidor: una máquina de la LAN, una VM, un servidor físico de la oficina, etc. WardNode no impone ninguna restricción sobre rangos de IP privados — http://192.168.1.10:8088 se registra y funciona exactamente igual que cualquier otro upstream.

4.1 El modelo de upstream

No existe validación que bloquee rangos RFC 1918 (192.168.x.x, 10.x.x.x, 172.16–31.x.x). Al guardar el sitio, la consola genera:

proxy_pass http://192.168.1.10:8088;

No hay paso adicional en WardNode. La restricción es puramente de conectividad de red entre el servidor y esa IP.

4.2 El requisito real: conectividad entre el servidor y la LAN

El proxy usa la red del servidor directamente. Si WardNode está en un VPS público, ese VPS no tiene ruta hacia tu red local (192.168.x.x) a menos que configures un túnel.

Lo que network_mode: host no resuelve: que el paquete llegue físicamente a 192.168.1.10. Sin un túnel configurado en el servidor, el proxy enviará tráfico a esa IP y no encontrará ruta. El comando ping 192.168.1.10 desde el servidor debe funcionar antes de registrar el sitio.

4.3 Opciones de túnel (de más a menos recomendable)

OpciónCómo funcionaCuándo usarla
WireGuard site-to-site Interfaz wg0 en el servidor y en un nodo LAN. El servidor gana ruta estática a 192.168.x.x/24 vía la interfaz WireGuard. Producción. Ligero, rápido, sin overhead de gestión de nube.
Tailscale / Headscale Instalar el agente en el servidor y en el nodo LAN. Publicar la subred con --advertise-routes=192.168.1.0/24 desde el nodo LAN. La opción más rápida de montar. Ideal para equipos pequeños.
Túnel SSH inverso El nodo LAN abre ssh -R 8088:192.168.1.10:8088 usuario@servidor. El upstream apunta a http://127.0.0.1:8088 (Alcance B). Pruebas o acceso puntual. Frágil para producción — no sobrevive reinicios.
Cloudflare Tunnel / ngrok El servicio LAN inicia una conexión saliente hacia la nube. No proxeas tú la IP — lo hace el proveedor. Cuando no controlas el firewall ni el router de la LAN.

4.4 Ejemplo mínimo con WireGuard

# ── En el servidor (VPS) ────────────────────────────────
apt install wireguard

# /etc/wireguard/wg0.conf

# ── Verificar y registrar ────────────────────────────────

# En WardNode → Nuevo sitio → upstream_url = http://192.168.1.10:8088

4.5 Host header — apps que validan el dominio

WardNode envía proxy_set_header Host $host; (el dominio público, ej. mi-app.ejemplo.com). Si la aplicación LAN valida que el Host coincida con su nombre interno, puede rechazar las peticiones.

Solución: en la vista del sitio → Configuración extra de Nginx, añade: 
proxy_set_header Host servidor-interno.lan;
Este override se valida y se incluye en el .conf generado, aplicando solo a ese sitio.
Nota de seguridad (SSRF): el campo upstream_url no valida rangos de IP. Un operador con permisos podría apuntar el upstream a servicios internos del servidor (metadatos de nube, APIs internas, etc.). En instalaciones con múltiples operadores, evalúa limitar quién puede crear o modificar sitios.

Comandos de diagnóstico de conectividad

# Verificar que el proxy puede alcanzar el upstream (ejecutar en el servidor)
ping 192.168.1.10
curl -I http://192.168.1.10:8088
curl -I http://127.0.0.1:3000

# Ver rutas disponibles (detectar si hay ruta hacia la LAN)
ip route show

# Verificar estado del túnel WireGuard (si aplica)
wg show

# Ver puertos publicados por contenedores al host
ss -tlnp | grep LISTEN

Pasos para registrar un sitio (cualquier alcance)

  1. Verifica la conectividad: el comando curl -I http://<upstream> desde el servidor debe responder.
  2. En Proxy & WAF → Sitios, haz clic en Nuevo sitio.
  3. Introduce el dominio público y la URL del upstream según el alcance.
  4. Guarda — la consola regenera los .conf de Nginx y recarga el proxy automáticamente.
  5. Apunta el registro DNS del dominio a la IP pública del servidor.
  6. Opcionalmente, activa TLS con Let's Encrypt desde la vista de detalle del sitio.
{# ── 6. Qué es el WAF ───────────────────────────────────────────── #}

6 · Qué es el WAF (ModSecurity + OWASP CRS)

WardNode incorpora un Web Application Firewall (WAF) basado en dos componentes que trabajan juntos:

  • ModSecurity — motor de inspección HTTP que evalúa cada petición y respuesta contra un conjunto de reglas. Está embebido en el contenedor proxy como módulo de Nginx.
  • OWASP Core Rule Set (CRS) — colección de reglas de detección para los ataques web más comunes (SQLi, XSS, LFI, RCE, etc.), mantenida por la fundación OWASP. WardNode usa la imagen oficial owasp/modsecurity-crs:nginx.

El CRS usa un modelo de puntuación por anomalía: cada regla que dispara acumula puntos. Cuando la puntuación de una petición supera el umbral configurado, ModSecurity la bloquea (en modo bloqueo) o la registra (en modo solo detección). Los eventos quedan visibles en Eventos y en los KPIs del Overview.

Parámetros globales (fijos, baked-in en la imagen)

Paranoia level = 1 y anomaly threshold = valores por defecto de la imagen.
Estos parámetros están configurados en proxy/modsecurity/modsecurity-override.conf y no son editables desde la UI de WardNode. Cambiarlos requiere editar ese archivo y reconstruir la imagen del proxy (docker compose build proxy). El nivel de paranoia 1 es el más equilibrado: detecta los ataques más obvios con pocos falsos positivos.

Modos de operación del WAF

ModoDirectiva generadaComportamientoCuándo usarlo
Bloqueo SecRuleEngine On Las peticiones que superan el umbral reciben HTTP 403 y no llegan al upstream. Producción, tras afinar las reglas con el modo detección.
Solo detección SecRuleEngine DetectionOnly Las reglas se evalúan y los ataques se registran en Eventos, pero no se bloquea ninguna petición. Puesta en marcha, análisis de falsos positivos, pruebas A/B de reglas.

En ambos modos modsecurity on; siempre está activo — la diferencia es solo si el motor actúa o solo registra.

{# ── 7. Estado del WAF ───────────────────────────────────────────── #}

7 · Estado del WAF

Acceso: Proxy & WAF → [sitio] → Estado del WAF (columna derecha del detalle del sitio). El switch "Bloqueo de ataques" controla si el WAF bloquea o solo detecta.

SwitchGeneraEfecto
✅ Activado SecRuleEngine On Modo bloqueo — las peticiones que disparan reglas reciben HTTP 403.
☐ Desactivado SecRuleEngine DetectionOnly Modo solo detección — los ataques se registran en Eventos pero no se bloquean. Útil para afinar reglas antes de activar el bloqueo.
Flujo recomendado para un sitio nuevo:
1. Crear el sitio con WAF en modo solo detección.
2. Dejar correr tráfico real durante 24–48 h y revisar Eventos en busca de falsos positivos.
3. Desactivar las categorías CRS o añadir excepciones por ID para los falsos positivos identificados.
4. Activar el switch de bloqueo.

Cómo actúa sobre la configuración generada

Al desactivar una categoría, el archivo .conf del sitio incluye:

SecRuleRemoveByTag "attack-sqli"       # ejemplo para la categoría sqli
SecRuleRemoveByTag "OWASP_CRS/AUTOMATION"  # ejemplo para scanner

Cada categoría tiene su crs_tag específico. Solo se generan entradas SecRuleRemoveByTag para las categorías desactivadas; las activas simplemente no producen ninguna directiva de exclusión.

{# ── 9. Reglas personalizadas ────────────────────────────────────── #}

9 · Reglas personalizadas ModSecurity

Acceso: Proxy & WAF → [sitio] → Reglas personalizadas ModSecurity. Permiten añadir directivas SecRule o SecAction propias que se insertan en el bloque ModSecurity del sitio, después de las reglas CRS.

Formato válido

Cada regla debe empezar por SecRule o SecAction y llevar una acción id: en el rango reservado para reglas personalizadas de WardNode:

# Bloquear un user-agent específico
SecRule REQUEST_HEADERS:User-Agent "@contains badbot" \
    "id:1000001,phase:1,deny,status:403,log,msg:'Bot bloqueado'"

# Excluir un parámetro de la inspección SQLi (SecAction)
SecAction "id:1000002,phase:1,pass,nolog,setvar:tx.sql_injection_score=0"

Reglas de validación

RestricciónDetalle
Rango de IDs obligatorio1.000.000 – 1.999.999. Los IDs del CRS oficial (900000–999999) no pueden usarse aquí.
IDs únicos por sitioNo se permiten dos reglas con el mismo ID en el mismo sitio.
Solo SecRule / SecActionOtros statements (SecPolicy, SecComponentSignature…) son rechazados.
Sin comillas simplesUsar comillas dobles para todos los valores.
Sin tokens peligrososinclude, exec:, lua: y ctl: están prohibidos.
Máx. 6.000 caracteresPor regla (suma de nombre + texto).
Activar/desactivar sin borrar: cada regla tiene un switch de habilitación. Una regla desactivada no se incluye en el .conf generado pero permanece en la base de datos para su reutilización posterior.
{# ── 10. Excepciones WAF ─────────────────────────────────────────── #}

10 · Excepciones WAF

Acceso: Proxy & WAF → [sitio] → Excepciones WAF. Permiten silenciar una regla CRS concreta por su ID cuando genera falsos positivos para un sitio específico. La excepción solo afecta a ese sitio — los demás sitios no se ven alterados.

Diferencia con desactivar una categoría completa

MecanismoGranularidadCuándo usarlo
Categoría CRS off Desactiva todas las reglas de esa categoría (SecRuleRemoveByTag) La categoría entera genera falsos positivos para esta aplicación.
Excepción por ID Desactiva una sola regla (SecRuleRemoveById) Solo una regla específica del CRS genera falsos positivos. Minimiza la superficie expuesta.

Rango válido y restricciones

Solo se aceptan IDs del rango del CRS oficial: 900000 – 999999. Los IDs de reglas personalizadas (1000000–1999999) no son excluibles aquí — para desactivarlas, usa el switch de habilitación en "Reglas personalizadas".

Reglas críticas que no pueden excluirse:
Las siguientes reglas protegen el proceso de scoring y bloqueo del CRS. WardNode rechaza intentos de excluirlas:
  • 901001–901420 — Inicialización del motor CRS
  • 949110, 949111 — Bloqueo por anomaly score entrante
  • 959100 — Bloqueo por anomaly score saliente
  • 980130, 980140, 980170 — Correlación y scoring final

El campo "Comentario / motivo" (máx. 200 caracteres) permite registrar la razón de la excepción para auditoría.

{# ── 11. Cabeceras de seguridad ──────────────────────────────────── #}

11 · Cabeceras de seguridad

Acceso: Proxy & WAF → [sitio] → Cabeceras de seguridad. El proxy inyecta headers HTTP en cada respuesta que pasa por el WAF. WardNode pre-configura un conjunto de cabeceras por defecto y permite añadir o modificar headers personalizados.

Headers por defecto

HeaderValor por defectoActivoQué protege
X-Content-Type-Optionsnosniff✅Evita que el navegador interprete el tipo MIME incorrecto (MIME sniffing).
X-Frame-OptionsDENY✅Previene que el sitio sea embebido en iframes (clickjacking).
Referrer-Policystrict-origin-when-cross-origin✅Controla qué información de referencia se envía a terceros.
Permissions-Policycamera=(), microphone=(), geolocation=()✅Deshabilita acceso a cámara, micrófono y geolocalización.
X-XSS-Protection1; mode=block✅Activa el filtro XSS del navegador (legacy; útil para IE/Edge antiguos).
Content-Security-PolicyPolítica WardNode por defecto☐Define orígenes permitidos para scripts, estilos e iframes. Desactivado porque cada app define su propia CSP.
Strict-Transport-Security——Gestionado por el selector HSTS del panel TLS — no configurar aquí.

Columna "Siempre"

El flag Siempre (always en nginx) indica que el header se añade también en respuestas de error (4xx, 5xx) y redirecciones (3xx), no solo en las respuestas 2xx. Se recomienda activarlo para todos los headers de seguridad.

Headers personalizados

Se pueden añadir headers propios con cualquier nombre que cumpla el estándar HTTP (solo caracteres A-Za-z0-9!#$%&'*+.^_`|~-, sin caracteres de control en el valor). Útil para headers no incluidos en los defaults, como Cross-Origin-Opener-Policy o Cross-Origin-Resource-Policy.

12 · Política de tráfico

Acceso: Proxy & WAF → [sitio] → Politica de trafico. Configura los mecanismos limit_req y limit_conn de Nginx para mitigar ataques de fuerza bruta y DoS a nivel de conexión.

Parámetros configurables

ParámetroDescripciónDefaultRango

BurstPeticiones adicionales en cola permitidas temporalmente sobre la tasa.1000 – 20.000

Atención — X-Forwarded-For puede ser falsificado:
La clave X-Forwarded-For permite que un atacante rote su IP aparente simplemente cambiando el header, evadiendo el rate limiting. Usa esta opción solo si WardNode está detrás de un load balancer de confianza que sobreescribe ese header. En todos los demás casos usa IP remota.

Qué genera en la configuración Nginx

La política genera zonas globales en generated/nginx/00-zones.conf y directivas dentro del location / de cada sitio:

# 00-zones.conf (global, agregado de todos los sitios)
limit_req_zone  $binary_remote_addr  zone=req_site_1:10m  rate=50r/s;
limit_conn_zone $binary_remote_addr  zone=conn_site_1:10m;

# site-ejemplo.conf (dentro del location /)
limit_req  zone=req_site_1  burst=100  nodelay;
limit_conn zone=conn_site_1 20;

Cuando el rate limit se supera, Nginx devuelve HTTP 429 Too Many Requests (o 503 si el burst también se agota con nodelay).

{# ── 13. TLS y certificados ──────────────────────────────────────── #}

13 · TLS y certificados

Acceso: Proxy & WAF → [sitio] → TLS y certificados. Controla si el sitio sirve tráfico HTTPS, qué certificado usa y cómo gestiona el redirect HTTP.

Modos de certificado

ModoConfiguraciónCuándo usarlo
Let's Encrypt Activar switch "Usar Let's Encrypt" + email de contacto. WardNode lanza certbot en modo webroot contra el contenedor proxy y guarda el cert en /etc/letsencrypt/live/{dominio}/. La provisión activa automáticamente "Forzar HTTPS". Dominios públicos accesibles desde internet. El dominio debe apuntar a la IP del servidor antes de provisionar.
Certificado propio Introducir la ruta al archivo .crt/.pem (Certificado personalizado) y la ruta a la clave privada (Llave privada personalizada). Las rutas deben ser accesibles desde dentro del contenedor proxy. Certificados de CA interna, wildcards, o dominios sin acceso público a internet.
Sin TLS (HTTP) No activar ninguna opción de certificado. Entorno de desarrollo o cuando TLS se gestiona en una capa exterior (CDN, balanceador).

Forzar HTTPS (redirect 301)

El switch "Forzar HTTPS" genera un bloque server { listen 80; return 301 https://… } separado que redirige todo el tráfico HTTP al HTTPS equivalente. La ruta /.well-known/acme-challenge/ queda exenta del redirect para permitir renovaciones de Let's Encrypt.

HSTS (Strict-Transport-Security)

El selector HSTS añade el header Strict-Transport-Security con las opciones más comunes:

OpciónHeader generadoEfecto
Desactivado—No se añade el header.
1 añomax-age=31536000El navegador recuerda usar HTTPS durante 1 año.
1 año + includeSubDomains (recomendado)max-age=31536000; includeSubDomainsAplica también a todos los subdominios.
1 año + includeSubDomains + preloadmax-age=31536000; includeSubDomains; preloadPermite incluir el dominio en la lista HSTS preload de los navegadores. Solo usar si tienes TLS en todos los subdominios.
Orden recomendado: activar TLS → Forzar HTTPS → luego HSTS. Activar HSTS sin TLS activo o sin Forzar HTTPS puede dejar el sitio inaccesible desde navegadores que ya memorizaron el header.
{# ── 14. Protección contra bots ──────────────────────────────────── #}

14 · Protección contra bots

Acceso: Proxy & WAF → [sitio] → Protección contra bots. Añade una capa de desafío matemático (tipo CAPTCHA ligero, sin servicio externo) para filtrar bots simples antes de que lleguen al upstream.

Cómo funciona

  1. Un visitante nuevo llega al sitio sin la cookie wn_bot.
  2. Nginx redirige la petición a /_wn_challenge/ — una página HTML+JavaScript embebida en el proxy que presenta un desafío matemático simple.
  3. El navegador (o el bot) debe resolver el desafío y enviar la respuesta. Un bot sin motor JS habitualmente falla.
  4. Al resolver correctamente, el proxy establece la cookie wn_bot=ward_cleared_v1 con duración de 1 hora.
  5. Las peticiones posteriores con esa cookie pasan directamente al upstream sin volver a ver el desafío.
Cuándo activarlo: sitios con tráfico mayoritariamente humano que estén sufriendo scraping, ataques de credential stuffing o DoS de bots simples. No es una solución robusta contra bots con motor JavaScript. Para bots sofisticados considera complementarlo con las reglas CRS de detección de escáneres (scanner) y el módulo CrowdSec (WardNode CS).

Puedes ver cómo se verá el desafío usando el enlace "Ver desafío" disponible en la tarjeta de Protección contra bots.

{# ── 15. Bloqueo por país (GeoIP) ────────────────────────────────── #}

15 · Bloqueo por país (GeoIP)

Acceso: Proxy & WAF → [sitio] → Bloqueo por país (GeoIP). Bloquea el tráfico originado en un país a nivel Nginx, antes de que llegue al WAF o al upstream. Cada entrada es por sitio — bloquear un país en un sitio no afecta a los demás.

Qué genera

Al añadir un país, se escribe un archivo de mapa (generated/nginx/10-blocklist-site-{id}.map) y el bloque del sitio incluye:

if ($geo_blocked_site_1) {
    return 444;   # Cierra la conexión TCP sin respuesta HTTP
}

El código 444 es una extensión de Nginx que cierra la conexión silenciosamente — el cliente no recibe ninguna respuesta HTTP, ni siquiera un error.

Requisito: base de datos GeoIP MaxMind

El bloqueo geográfico requiere la base de datos GeoLite2-Country de MaxMind, que no se incluye en WardNode. Para activarla: ve a Ajustes → GeoIP — MaxMind, introduce tus credenciales (cuenta MaxMind gratuita) y descarga la base. Mientras no esté disponible, la variable $geo_blocked_site_N vale siempre 0 y no se bloquea nada.

Diferencia con el rate limiting

El bloqueo por país es binario (bloquea todo el tráfico de ese país para ese sitio); el rate limiting controla la frecuencia de peticiones. Se pueden usar juntos: bloquear países de alto riesgo y aplicar rate limit al resto.

16 · Nginx extra

Acceso: Proxy & WAF → [sitio] → Nginx extra. Permite inyectar directivas Nginx personalizadas y validadas dentro del bloque server {} o dentro del location / {} del sitio. Es una vía de escape para casos que no cubren los controles de la UI.

Dos bloques disponibles

BloqueDónde se insertaUso típico
Directivas en server Dentro del bloque server {}, fuera del location / client_max_body_size 20m;, keepalive_timeout 30;, directivas SSL adicionales.
Directivas en location / Dentro del bloque location / {} proxy_buffering off;, proxy_read_timeout 120s;, override de headers de proxy.

Ejemplo: corregir el header Host hacia una aplicación interna

Si la aplicación LAN valida que el header Host coincida con su nombre interno (ver sección 4.5), añade en el bloque "Directivas en location /":

proxy_set_header Host servidor-interno.lan;

RestricciónMotivo
