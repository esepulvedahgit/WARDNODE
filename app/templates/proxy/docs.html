1 · Visión general del plano de proxy

WardNode separa completamente el plano de gestión del plano de tráfico. La consola Flask (puerto 5000) nunca maneja tráfico de usuarios finales: solo genera archivos de configuración Nginx que el contenedor proxy lee y aplica.

Tráfico externo (internet)
      │  80 / 443
      ▼
┌──────────────────────────────────────────┐
│  Contenedor proxy                        │
│  Nginx + ModSecurity (OWASP CRS)         │
│                                          │
│  Lee: /etc/nginx/generated/*.conf        │  ◄── generados por la consola
│  Aplica: WAF, TLS, rate limit, headers   │
└──────────────────────┬───────────────────┘
                       │  proxy_pass http://upstream:puerto
                       ▼
              Aplicación protegida
              (contenedor, VM, host, LAN…)

┌──────────────────────────────────────────┐
│  Consola Flask  (puerto 5000)            │
│  Solo plano de gestión                   │
│  Escribe  →  generated/nginx/*.conf      │
│  Recarga  →  docker exec nginx -s reload │
└──────────────────────────────────────────┘

Cómo se define el destino de cada sitio

Cada sitio registrado tiene un campo upstream_url (por ejemplo http://app:8080 o https://192.168.1.50:443). La consola lo parsea con urlparse y genera directamente:

proxy_pass http://<host>:<puerto>;
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

El valor se inyecta tal cual en el .conf — no se usa un bloque upstream {} nombrado. Cualquier host resoluble o IP alcanzable por el contenedor proxy es un upstream válido.

Nota: el módulo WF (WardNode Firewall) solo aplica para upstreams loopback exactos (127.0.0.1, localhost, host.docker.internal) del propio host. Las IPs de red privada (LAN) no pasan por ese flujo — se tratan como cualquier otro upstream remoto.

2 · VPS público → servidores en la LAN

Un despliegue habitual es instalar WardNode en un VPS con IP pública y usar su proxy para exponer aplicaciones que corren en una red local (casa, oficina, datacenter privado). Este escenario está completamente soportado sin ninguna adaptación de código.

2.1 El modelo de upstream

El campo upstream_url acepta cualquier URL con IP o hostname. No existe validación que bloquee rangos RFC 1918 (192.168.x.x, 10.x.x.x, 172.16–31.x.x):

Upstream¿Permitido?Observación
http://192.168.1.50:8080✅ SíIP LAN privada — se trata como upstream remoto normal
http://10.0.0.20:3000✅ SíIdem — cualquier RFC 1918
https://192.168.1.100:443✅ SíTLS hacia servidor LAN
http://127.0.0.1:8080⚠️ Con restricciónLoopback local — requiere módulo WF y puerto no reservado
http://127.0.0.1:80❌ NoLoopback + puerto reservado (80/443/22/5000)

Al registrar el sitio con upstream_url = http://192.168.1.50:8080, la consola genera y el proxy aplica inmediatamente proxy_pass http://192.168.1.50:8080;. No hay paso adicional en WardNode.

2.2 El requisito real: conectividad de red

El contenedor proxy usa network_mode: host en producción (docker-compose.vps.yml): comparte directamente la pila de red del VPS. Esto significa que puede alcanzar cualquier red que el VPS pueda rutear. El problema es que un VPS público no tiene ruta a tu LAN sin un túnel — esas IPs privadas viven detrás del NAT de tu red local.

Lo que network_mode: host no resuelve: que el paquete llegue físicamente a 192.168.1.50. Sin un túnel configurado en el VPS, el proxy intentará enviar tráfico a esa IP y no encontrará ruta.

2.3 Opciones de túnel (de más a menos recomendable)

OpciónCómo funcionaCuándo usarla
WireGuard site-to-site Interfaz wg0 en el VPS y en un nodo LAN. El VPS gana ruta estática a 192.168.x.x/24 vía la interfaz WireGuard. Producción. Ligero, rápido, sin overhead de gestión de nube.
Tailscale / Headscale Instalar el agente en el VPS y en el nodo LAN. Publicar la subred con --advertise-routes=192.168.1.0/24 desde el nodo LAN. La opción más rápida de montar. Ideal para equipos pequeños.
Túnel SSH inverso El nodo LAN abre ssh -R 8080:servidor-local:8080 usuario@vps. El upstream del sitio apunta a http://127.0.0.1:8080 (loopback del VPS). Pruebas o acceso puntual. Frágil para producción — no sobrevive reinicios.
Cloudflare Tunnel / ngrok El servicio LAN inicia una conexión saliente hacia la nube. Cambia el modelo: no proxeas tú la IP, Cloudflare/ngrok lo hacen. Cuando no controlas el firewall ni el router de la LAN.

2.4 Ejemplo mínimo con WireGuard

Con WireGuard activo, el proxy ve la LAN como una red local más. El flujo completo:

# En el VPS — instalar y configurar WireGuard
apt install wireguard
# /etc/wireguard/wg0.conf (VPS)
[Interface]
Address = 10.10.0.1/24
ListenPort = 51820
PrivateKey = <clave-privada-vps>

[Peer]
PublicKey = <clave-publica-nodo-lan>
AllowedIPs = 10.10.0.2/32, 192.168.1.0/24   # ← subred LAN completa
Endpoint = <IP-nodo-lan>:51820

# Levantar
wg-quick up wg0

# En el nodo LAN (el que tiene acceso a 192.168.1.0/24)
# /etc/wireguard/wg0.conf (nodo LAN)
[Interface]
Address = 10.10.0.2/24
PrivateKey = <clave-privada-nodo-lan>

[Peer]
PublicKey = <clave-publica-vps>
AllowedIPs = 0.0.0.0/0
Endpoint = <IP-publica-vps>:51820
PersistentKeepalive = 25

wg-quick up wg0

Una vez el túnel está activo, desde el VPS puedes hacer ping 192.168.1.50 sin problema. Luego en WardNode, registra el sitio con upstream_url = http://192.168.1.50:8080 y ya.

2.5 Host header — apps que validan el dominio

WardNode envía siempre proxy_set_header Host $host;, donde $host es el dominio público (p. ej. mi-app.ejemplo.com). Si la aplicación LAN valida que el Host header coincida con su nombre interno, puede rechazar las peticiones.

Solución: en la vista de detalle del sitio, ve a Configuración extra de Nginx y añade un bloque de tipo location o server con: 
proxy_set_header Host app-interna.lan;
Este override se valida y se incluye en el .conf generado, sobreescribiendo el header por defecto solo para ese sitio.
Nota de seguridad (SSRF): como el campo upstream_url de un sitio no valida rangos de IP, un operador con permisos podría configurar el upstream apuntando a servicios internos del propio VPS (metadatos de nube, APIs internas, etc.). En instalaciones con múltiples operadores, evalúa restringir quién puede crear o modificar sitios.

Comandos útiles en el VPS tras configurar WireGuard

# Verificar que el túnel esté activo
wg show

# Comprobar conectividad desde el VPS al servidor LAN
ping 192.168.1.50
curl -I http://192.168.1.50:8080

# Ver la ruta hacia la LAN
ip route show | grep 192.168

Pasos para registrar un sitio LAN en WardNode

  1. Asegúrate de que el túnel está activo y el VPS puede hacer ping a la IP del servidor LAN.
  2. En Proxy & WAF → Sitios, haz clic en Nuevo sitio.
  3. Introduce el dominio público (p. ej. app.ejemplo.com) y la URL del upstream LAN (p. ej. http://192.168.1.50:8080).
  4. Guarda — la consola regenera los .conf de Nginx y recarga el proxy automáticamente.
  5. Apunta el registro DNS del dominio a la IP pública del VPS.
  6. Opcionalmente, activa TLS con Let's Encrypt desde la vista de detalle del sitio.
