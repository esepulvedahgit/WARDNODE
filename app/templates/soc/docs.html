1 · Visión general

El módulo SOC convierte el flujo crudo de eventos del WAF (AttackEvent) en incidentes accionables: agrupa la actividad de cada IP atacante, la puntúa, la enriquece con threat intel, la explica con un LLM y notifica al operador.

Tráfico atacante
      │
      ▼
┌─────────────┐  logs JSON   ┌──────────────────┐
│ Proxy Nginx │ ───────────► │ Ingest thread    │ ──► AttackEvent (DB)
│ ModSecurity │   (stdout)   │ (modsec-ingest)  │
└─────────────┘              └──────────────────┘
                                                      cada N minutos
┌────────────────────────────────────────────────────────────────────┐
│ soc-worker (thread daemon + advisory lock PostgreSQL)              │
│                                                                    │
│  1. DETECCIÓN heurística (SQL agregado por IP)                     │
│  2. Scoring ML (IsolationForest, opcional)                         │
│  3. ENRIQUECIMIENTO (AbuseIPDB + MITRE ATT&CK)                     │
│  4. Creación/actualización del INCIDENTE (dedupe)                  │
│  5. ANÁLISIS LLM (opt-in, solo incidentes elegibles)               │
│  6. ALERTAS (email / Telegram, opt-in)                             │
│  7. Reentrenamiento ML (time-gated)                                │
└────────────────────────────────────────────────────────────────────┘
      │
      ▼
UI /soc/  →  dashboard · bitácora · detalle · campana  →  revisión humana
Principio rector: cada etapa degrada con gracia. Sin API keys → solo heurísticas. Sin SMTP/Telegram → sin alertas pero con incidentes. Sin histórico → sin ML. La detección nunca se detiene.
{# ── 2. Por qué se dispara un incidente ──────────────────────── #}

2 · ¿Por qué se dispara un incidente?

Es la decisión central del módulo (app/soc/detect.py).

2.1 La condición de entrada (filtro duro)

≥ 20 eventos WAF de la MISMA IP dentro de los últimos 15 minutos

Es la única condición que convierte una IP en candidata a incidente:

  • Solo cuentan eventos que ModSecurity ya marcó (bloqueos o detecciones). El tráfico legítimo jamás entra al conteo.
  • Se agrupa solo por IP origen: un atacante que barre varios dominios es UN único incidente.
  • Las IPs no parseables se descartan; las IPs privadas sí se aceptan (un atacante interno es un incidente válido).
ParámetroClave AppConfigDefault
Ventana de correlaciónsoc_window_minutes15 min
Mínimo de eventossoc_threshold_events20
⚠️ Limitación conocida (criterio volumétrico): 19 eventos en 15 minutos = ningún incidente, aunque los payloads sean graves. Un atacante low-and-slow (1 request por hora) no genera incidente. Los eventos sueltos siguen visibles en Eventos WAF.

2.2 El score heurístico (decide la severidad, no la existencia)

Superado el umbral, el incidente se crea siempre. El score 0–100 solo gradúa su gravedad:

score = volumen       (0–40)  =  40 × eventos / (2 × umbral)
      + diversidad    (0–20)  =  5 × nº de categorías CRS distintas
      + ratio bloqueo (0–20)  =  20 × (eventos bloqueados / total)
      + fan-out       (0–20)  =  2 × nº de paths distintos
ComponentePregunta que responde
Volumen¿Cuánto martilla? (satura a 40 con 2× el umbral)
Diversidad¿Prueba varias clases de ataque (SQLi + XSS + LFI…)?
Ratio de bloqueo¿El WAF lo está frenando activamente?
Fan-out¿Escanea muchas rutas distintas (recon/scanner)?
ScoreSeveridad
≥ 80critical
≥ 60high
≥ 40medium
< 40low

2.3 Los tres modificadores posteriores

  1. Score ML (si está activo y hay modelo): la severidad se calcula sobre max(score_heurístico, ml_score). El ML solo puede SUBIR la severidad, nunca bajarla.
  2. Reputación AbuseIPDB: si abuseConfidenceScore ≥ 75, la severidad sube un nivel (ej. high → critical).
  3. Dedupe: si ya existe un incidente nuevo de esa IP en la última hora, no se crea otro — se actualiza el existente (eventos, score y severidad solo al alza).

2.4 Ejemplos concretos

✅ Genera incidente — 50 requests SQLi + XSS contra 30 paths en 10 minutos, todo bloqueado:

volumen    = min(40, 40 × 50/40)  = 40
diversidad = min(20, 5 × 2)       = 10
bloqueo    = 20 × (50/50)         = 20
fan-out    = min(20, 2 × 30)      = 20
                            score = 90 → critical

❌ NO genera incidente:

  • 19 eventos en 15 minutos (no alcanza el umbral).
  • 5 requests RCE aislados (graves, pero volumétricamente insuficientes).
  • 1 request por hora durante un día (low-and-slow).

🔁 NO genera un SEGUNDO incidente: la misma IP sigue atacando 20 minutos después → el dedupe actualiza el incidente abierto, no crea otro ni dispara otra alerta.

{# ── 3. Ciclo del worker ─────────────────────────────────────── #}

3 · Ciclo del worker

Thread daemon soc-worker que arranca con la aplicación (app/soc/worker.py).

AspectoValor
Tick del loopcada 15 s (comprueba si toca trabajar)
Intervalo real del ciclosoc_worker_interval_min (default 5 min, rango 1–60)
Delay tras boot60 s
Backoff tras error30 s
  • Módulo apagado: el thread queda ocioso (costo ~0). Se puede activar sin reiniciar.
  • Multi-worker (gunicorn + PostgreSQL): un advisory lock garantiza que solo un proceso ejecute el ciclo y el reentrenamiento ML.
  • Primera ejecución: si la tabla MITRE local está vacía, descarga el CTI oficial una única vez.
El SOC no es tiempo real puro: un ataque se convierte en incidente como máximo ~intervalo minutos después (default ≤ 5 min).
{# ── 4. Enriquecimiento ──────────────────────────────────────── #}

4 · Enriquecimiento del incidente

Nunca bloquea la creación del incidente: cualquier fallo degrada con gracia (enrich.py, mitre_cti.py).

4.1 AbuseIPDB (reputación de la IP)

ControlValor
Solo IPs públicasprivadas/loopback/reservadas → no se consulta (no se envían datos atacante-controlados a terceros)
Cache localTTL 24 h — IPs repetidas no consumen cuota
Tope por ciclo25 llamadas — protege la cuota free (1.000/día)
Tope de respuesta256 KB
Efectoscore ≥ 75 sube la severidad un nivel

4.2 MITRE ATT&CK

  • Mapeo estático categoría CRS → técnicas (ej. sql-injection → T1190, scanner → T1595/T1046, brute-force → T1110).
  • Si la base CTI local está sincronizada (botón en Configuración o sync automática inicial), los nombres y tácticas se toman de ahí (~650 técnicas Enterprise del CTI oficial).
  • La misma base valida los IDs que sugiere el LLM: un ID inexistente en ATT&CK real se descarta (anti-alucinación).
{# ── 5. Análisis LLM ─────────────────────────────────────────── #}

5 · Análisis con IA (LLM)

5.1 Los 4 guards (todos deben cumplirse)

1. Opt-in de datos       soc_data_optin == "1"   (checkbox explícito; default OFF)
2. Severidad ≥ umbral    soc_analyze_min_severity (default "medium")
3. Proveedor disponible  alguna API key configurada (con fallback automático)
4. Sin análisis previo   un incidente se analiza UNA sola vez

Además: máximo 5 análisis por ciclo, priorizando los de mayor severidad (control de costos).

5.2 Qué se envía (minimización de datos)

Solo metadatos agregados: IP, dominio, ventana, conteos, categorías CRS, reglas disparadas, top de paths truncados a 120 chars, scores y el contexto MITRE autorizado. Nunca bodies de peticiones ni mensajes completos de ModSecurity. Los valores atacante-controlados se neutralizan (defensa anti prompt-injection).

5.3 Proveedores y fallback

ProveedorModelo default
OpenRouteranthropic/claude-sonnet-4.5
Anthropicclaude-sonnet-4-5
OpenAIgpt-4o-mini
DeepSeekdeepseek-chat
Geminigemini-2.0-flash

Si el proveedor activo no tiene key, se recorre openrouter → anthropic → openai → deepseek → gemini y se usa el primero con key. Sin keys → solo heurísticas.

La salida (summary, hipótesis, recomendaciones, técnicas MITRE, IoCs) pasa por un normalizador tolerante que nunca lanza: enums inválidos se corrigen, listas se capan, IDs MITRE alucinados se descartan.

{# ── 6. Alertas ──────────────────────────────────────────────── #}

6 · Sistema de alertas

Apagado por defecto (opt-in). Código: app/soc/alerts.py.

6.1 La cadena de 7 condiciones (todas deben cumplirse)

1. Módulo SOC activo        module_soc_enabled == "1"
2. Worker corriendo          (siempre vivo, pero ocioso si el módulo está off)
3. Alertas habilitadas       soc_alerts_enabled == "1"      ← DEFAULT: OFF
4. Incidente NUEVO creado    solo al crearse (no por dedupe ni incidentes viejos)
5. Severidad ≥ umbral        soc_alert_min_severity (default "high")
6. Fuera del cooldown        sin otra alerta de la MISMA IP en
                             soc_alert_cooldown_min (default 60 min)
7. Canal configurado         email (SMTP global + destinos) y/o
                             telegram (bot token cifrado + chat_id)

6.2 Comportamiento

  • Anti-spam por diseño: dedupe (1 incidente/IP/hora) + cooldown (1 alerta/IP/cooldown).
  • Best-effort por canal: si SMTP falla pero Telegram funciona, llega la de Telegram. Si ambos fallan → soc.alert.failed en auditoría y el ciclo sigue.
  • Contenido mínimo: id, severidad, IP, dominio, conteos, scores, summary IA y link al detalle. Nunca paths de ataque ni payloads — el canal puede viajar en claro.
  • Secretos: el bot token se guarda cifrado y jamás aparece en logs ni auditoría.
  • La alerta se evalúa después del análisis LLM, para incluir el summary de la IA.
{# ── 7. Scoring ML ───────────────────────────────────────────── #}

7 · Scoring ML (IsolationForest)

Opt-in (soc_ml_enabled, default OFF). Código: app/soc/ml.py.

AspectoValor
AlgoritmoIsolationForest (scikit-learn), contamination="auto"
Features (6)event_count, cat_diversity, path_fanout, block_ratio, method_diversity, status_diversity
Datos de entrenamientoagregados por (IP, hora) de los últimos 14 días
Mínimo para entrenar100 muestras (sin histórico no hay ML)
Reentrenamientocada soc_ml_retrain_hours (default 24 h) o manual con «Entrenar ahora»
Persistenciablob en DB — consistente entre workers, sobrevive rebuilds
Regla clave: el heurístico es siempre el piso — severidad = f(max(score, ml_score)). Un modelo mal entrenado no puede degradar la detección.
  • El score 0–100 se calibra con el rango del training set (más anómalo → más alto).
  • Si las features del modelo guardado no coinciden con las del código, el modelo se descarta y se reentrena solo.
