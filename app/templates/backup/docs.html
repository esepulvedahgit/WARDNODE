1 · Visión general

WardNode genera backups cifrados en zip AES-256 (pyzipper) que contienen todo lo necesario para restaurar la instalación completa: base de datos, certificados TLS y estado del firewall del host.

El módulo está activo por defecto (module_backup_enabled) y no requiere configuración adicional para empezar a funcionar.

Los backups se almacenan en WARDNODE_BACKUP_DIR (default: /app/data/backups, volumen nombrado backups). El directorio persiste entre actualizaciones y reinicios del contenedor.

{# ── 2. Contenido del backup ─────────────────────────────────── #}

2 · Contenido del backup (ZIP AES-256)

Cada archivo de backup es un zip cifrado con AES-256 que contiene los siguientes componentes:

ComponenteQué contieneNota
db/wardnode.pgdump Volcado completo de la base de datos PostgreSQL (pg_dump -Fc) Incluye usuarios, sitios, reglas, eventos, configuración
tls/letsencrypt.tar.gz Certificados TLS gestionados por Let's Encrypt Del volumen letsencrypt
host/ufw-rules.txt Reglas UFW del firewall del host Solo si módulo WF activo
host/protected_ports.json Puertos Docker protegidos Solo si módulo WF activo
manifest.json Metadatos: versión de formato, cabecera Alembic, checksums SHA-256 Usado para validar la restauración
README-RESTORE.md Instrucciones de restauración paso a paso Se incluye dentro del zip
{# ── 3. Lo que NUNCA se incluye ──────────────────────────────── #}

3 · Lo que NUNCA se incluye

⚠️ El backup NO incluye WARDNODE_SECRET_KEY ni el archivo .env.
Esta clave es imprescindible para descifrar los secretos almacenados en la base de datos (MaxMind, SMTP, claves API SOC, etc.). Sin ella, incluso con el backup completo, los secretos cifrados en la base de datos serán irrecuperables.

Debes guardar WARDNODE_SECRET_KEY por separado, en un gestor de contraseñas o vault seguro. Sin ella, el backup es inútil aunque esté completo e íntegro.

{# ── 4. Programación y retención ─────────────────────────────── #}

4 · Programación y retención

El scheduler ejecuta un backup automático diariamente a la hora configurada (UTC). La configuración disponible es:

  • Hora de ejecución (backup_hour): hora del día en UTC en que se lanza el backup automático.
  • Retención (backup_retention): número máximo de backups a conservar. Al superar el límite, el backup más antiguo se elimina automáticamente.

Notificación por email

Si SMTP está configurado en Ajustes, el scheduler envía un email tras cada backup automático:

  • Si el zip es menor de backup_email_max_mb (default 20 MB): se adjunta el zip completo.
  • Si el zip supera ese límite: se envía solo una notificación con el estado del backup (sin adjunto).
  • En caso de error: se envía un email de alerta con el detalle del fallo.
{# ── 5. Ejecución manual y descarga ──────────────────────────── #}

5 · Ejecución manual y descarga

Desde la interfaz de Backups (Backups) puedes realizar las siguientes operaciones:

  • Generar backup ahora: crea un backup inmediatamente. La escritura es atómica (.zip.part → .zip) para evitar backups corruptos en caso de error.
  • Descargar: descarga el zip cifrado de un backup existente.
  • Eliminar: elimina un backup de la lista. Esta acción es irreversible.

El nombre de cada archivo sigue el patrón wardnode-backup-YYYYMMDD-HHMMSS.zip, que también actúa como guarda frente a traversal de rutas en las operaciones de descarga y eliminación.

{# ── 6. Restauración por UI ───────────────────────────────────── #}

6 · Restauración por UI

⚠️ La restauración es irreversible. Sobrescribe completamente la base de datos activa con los datos del backup. Este proceso no se puede deshacer.

Pasos de seguridad obligatorios

Antes de ejecutar la restauración, el sistema exige tres confirmaciones:

  1. Re-autenticación: introducir la contraseña del administrador actual.
  2. TOTP (si está activo): introducir el código de 6 dígitos de la app autenticadora.
  3. Confirmación textual: escribir RESTAURAR en el campo de confirmación.

Validaciones antes de restaurar

El sistema valida automáticamente el zip antes de aplicarlo:

  • Checksums SHA-256: verifica la integridad de todos los componentes del zip.
  • Versión Alembic: rechaza backups de una versión de base de datos más nueva (que requeriría una migración adicional antes de restaurar).
  • Seguridad del zip: valida lista blanca de archivos internos y aplica límites anti zip-bomb (ratio y tamaño máximo).
Después de restaurar, la sesión actual se cierra automáticamente — la base de datos restaurada tiene sus propios usuarios y contraseñas. Deberás iniciar sesión con las credenciales del backup restaurado.
{# ── 7. Restauración por CLI ──────────────────────────────────── #}

7 · Restauración por CLI

La restauración por CLI es útil en escenarios de recuperación ante desastre donde la UI no está disponible. Los comandos disponibles son:

# Restaurar (solicita la contraseña del zip interactivamente)
flask backup-restore <archivo.zip>

# Restaurar sin confirmación interactiva (útil en scripts)
flask backup-restore <archivo.zip> --yes

# Validar y extraer sin restaurar la base de datos
flask backup-restore <archivo.zip> --skip-db
Después del restore CLI: ejecutar flask db upgrade si hay migraciones pendientes, luego reiniciar la consola para que los cambios sean efectivos.

El proceso CLI aplica las mismas validaciones de integridad que la UI (checksums, versión Alembic, anti zip-bomb). La contraseña del zip es la misma que WARDNODE_SECRET_KEY usada al crear el backup.

{# ── 8. Referencia rápida — CLI ──────────────────────────────── #}

8 · Referencia rápida — CLI

ComandoAcción
flask backup-create Genera un backup ahora
flask backup-restore <zip> Restaura desde un zip (interactivo)
flask backup-prune [--keep N] Elimina los más antiguos, retiene N (default: valor de configuración)
